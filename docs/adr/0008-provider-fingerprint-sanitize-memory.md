# ADR-0008：供应商指纹记忆清洗 + 错误形状归一

- 状态：历史设计；v3.4 起自动清洗与记忆边界由 [升级说明](../UPGRADE-3.4.md) 取代。下文保留决策历史，不代表当前自动转发行为。
- 关联：`gateway/office_edge.py`；ADR-0003（通道识别）

## 背景

兼容策略是"透明优先，被上游拒绝后深清洗重试一次"（见架构文档 §5）。实测发现两条体验代价：

1. **双倍往返是常态而非例外**：Office 加载项会随请求携带 `metadata`、thinking 块、cache_control 等字段，而 DeepSeek 类 Anthropic 兼容端点拒绝其中一部分——同一供应商的每次请求都要先吃一次 4xx 再重试成功。切换供应商不会重置这个问题，用户每条消息都多付一次上游延迟与失败噪音。
2. **错误形状不归一**：非 Anthropic 系上游的错误 JSON 形状各异（`{"message": ...}`、纯文本等），加载项按官方 `{"type":"error","error":{...}}` 结构解析，形状不符时只能显示无名的 "Something went wrong"。

## 决策

**指纹记忆**：当某供应商的报文经深清洗重试成功后，记录"原始报文 vs 清洗后报文"的差异（被移除的顶层字段 + 内容块是否含需清理的形态），以**当前供应商 id** 为键存于内存。后续同一供应商的请求直接预应用这些差异，跳过注定失败的第一次往返。约束：

- 透明转发仍是默认——没学到的供应商永远先透明；
- 记忆只包含**已被该供应商实际拒绝过的差异**，不臆测；
- 切换供应商自动失效（键为 provider id）；进程重启清零，重新学习一次；
- 学习后的报文若仍被 4xx 拒绝，完整深清洗重试路径仍在兜底。

**错误归一**：上游 4xx/5xx 的响应体若不是 Anthropic 错误形状，包一层 `{"type":"error","error":{"type":"api_error","message":<原文/原信息>}}`——保留原状态码与原信息，只修形状，不伪造内容。已是 Anthropic 形状的原样透传。

## 被否掉的方案

- **全局记住"该上游需要清洗"然后每次全量 deep_sanitize**：会把该供应商本可支持的字段（如某些模型支持 thinking）也一并剥掉，过度损失透明性；
- **解析 4xx 文本精确记忆"是哪个字段被拒"**：错误文本格式因上游而异，脆弱；按"成功清洗的差异"记忆足够保守且可靠；
- **伪造 count_tokens 或伪造成功响应**：违反铁律"不伪造"，另案。

## 后果

- 兼容供应商（如真 Anthropic 或完全兼容端点）行为完全不变——它们从不触发重试，也就从不产生记忆；
- 不兼容供应商的第二条消息起，延迟与失败噪音显著下降（本机实测 DeepSeek：metadata 触发的双倍往返降为单次）；
- 记忆在内存中，不落盘，无隐私问题；
- e2e 测试锁定行为：第二次同形请求的上游命中次数应为 1 而非 2。
